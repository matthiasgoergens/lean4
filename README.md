# Benchmark harness, data and research record for the `Array.qsort` pattern-defeating quicksort PR

This orphan branch accompanies the pull request that replaces `Array.qsort` in Lean 4 core with a verified pattern-defeating quicksort (pdqsort), from the branch `matthias/qsort-pdq` of this fork.  It is not meant to be merged.  It holds the program and scripts that measured the PR's numbers, the raw data behind them, and the record of the design work that led to the choices in the PR, including what was tried and rejected.  Everything was written by Matthias Goergens.

The PR's numbers come from two builds of Lean: the PR's merge base (f4856ef9cd, "old") and the PR branch at 7d8ac86bab ("new").  The PR branch has since gained one documentation-only commit (fd6fd9957e, a doc comment in `src/Init/Data/Array/QSort/Basic.lean`); nothing measured here depends on it.

## What is where

* [`bench/`](bench/): the benchmark program and scripts used for the PR's numbers.  `Main.lean` and `lakefile.lean` are a small Lake project that uses only core's `Array.qsort` and `Array.qsortOrd` (plus an identity baseline that does not sort), so the same source can be compiled by either toolchain.  `PLAN.md` is the measurement plan, written before the timed runs.  The other files are the scripts listed under "How to reproduce".
* [`data/`](data/): the raw data and analyses behind the PR's tables.  [`data/README.md`](data/README.md) is the method and the results in full, with every figure of the PR's tables.  `data/runs/` holds one directory per run (`runs.tsv` with one row per measured process, the shard plans, the `perf` output of the `io_compute` and instruction-count runs) and the analysis outputs next to them.  `data/build/` and `data/verify/` hold the logs of building both toolchains, their fingerprints and the comparison of the source trees with the commits.
* [`research/`](research/): the record of the design work (below).

The measurements ran on one machine, referred to below as the benchmark machine: a 64-core (128 thread) AMD Ryzen Threadripper PRO 9985WX, shared with other users, with the `performance` governor.

## How to reproduce the PR's numbers

The scripts under `bench/` were written for the benchmark machine's layout and say so in their first comment lines: they expect to be run from `~/qsort-pr/bench/` (a copy of this branch's `bench/`), with the two toolchain trees at `~/qsort-pr/lean4-master` and `~/qsort-pr/lean4-branch`, podman, `sudo perf`, `uv`, and, for the block runs, CPUs 40 to 45 (six distinct physical cores) and CPU 40 for `io_compute`.  On another machine, change those CPU numbers and the `~/qsort-pr` root; nothing else is specific to it.  The steps:

1. Build the two Lean toolchains from a lean4 checkout: one tree at the merge base f4856ef9cd and one at the branch (7d8ac86bab for the measured numbers), each configured with `cmake --preset release -DUSE_GITHASH=OFF` and built with `make -C build/release -j32` inside a build container (`localhost/lean4-build`, built from the repository's own build instructions).  [`data/build-copy.sh`](data/build-copy.sh) does this for a copied tree and writes a log; [`data/build/`](data/build/) has the logs and [`toolchain-fingerprints.txt`](data/build/toolchain-fingerprints.txt) has the SHA-256 of the resulting `lean`, `lake`, `libleanshared.so` and so on.  Only stage 1 is used.
2. Check that the trees match the commits ([`data/verify/`](data/verify/) shows how, with `rsync --checksum --dry-run` against a fresh `git archive`).
3. `./build-bins.sh` builds the benchmark program 8 times with each toolchain, linked with `ld.lld --shuffle-sections` under seeds 1 to 8 ([`shuffled-build.sh`](bench/shuffled-build.sh), run inside the build container by `build-bins.sh`), into `bins/old/` and `bins/new/`.  Code placement is thus sampled instead of favouring one side.  The binaries' hashes are in [`data/runs/bins-fingerprints.tsv`](data/runs/bins-fingerprints.tsv).  Binaries are not part of this branch.
4. `./probe.sh` runs one checked run of each candidate workload to size the plan (which 1,000,000-element workloads the old sort finishes in time; output in [`data/runs/probe.log`](data/runs/probe.log)).  `./smoke-check.sh` runs every workload once with both builds, comparing the result with `Array.mergeSort` ([`data/runs/smoke-check.log`](data/runs/smoke-check.log)).
5. The randomised blocks: `./shards.py 1 runs/NAME 3 40 41 42 43 44 45` runs 18 complete blocks as six shards of three blocks, each shard pinned to its own core.  A block runs every cell of [`cells.py`](bench/cells.py) (each workload with `old`, `new` and the two baselines) once in a fresh random order; [`run.py`](bench/run.py) does the timing (each run one fresh process; each run picks one of the 8 layout builds at random through [`shuffled.sh`](bench/shuffled.sh)).  `cells.py ROUND CPU` writes the plan for a shard; the `cells-*.json` files in the data directories are the plans that were used.  The first block run is [`data/runs/2026-10-28-blocks/`](data/runs/2026-10-28-blocks/), made while the machine was busy.
6. `./quiet-run.sh runs/NAME 40 HOURS` waits until the 5-minute load average is below 40, then repeats the random-key and small-array workloads (round 2 of `cells.py`, 18 blocks) and the `io_compute` pairs.  [`data/runs/2026-10-29-quiet/`](data/runs/2026-10-29-quiet/) is that rerun, at a load of 11 to 15; the first attempt, which gave up after the load never fell, is [`data/runs/2026-10-28-quiet/wait.log`](data/runs/2026-10-28-quiet/wait.log).
7. `./io-compute.sh runs/NAME 10` compiles `tests/compile_bench/io_compute.lean` with each toolchain as that test's `run_test.sh` does and runs 10 pairs under `perf stat`, pinned to one CPU.  `./instr.sh runs/NAME` counts user-mode instructions (`perf stat -e instructions:u`) of the random-key and small-array workloads for layout seeds 1 to 3 of each build, with and without the sort, which is what the PR's instruction columns are.
8. The analyses: `analyse.py DIR old` (paired new / old ratios of the in-process sort time with 95% t intervals, and the hash check between old and new), `analyse_cpu.py DIR old` (the same for CPU time over the identity baseline), `control.py DIR` (the negative control: the two builds' baselines against each other), `table.py DIR` (the PR's table), `io_analyse.py DIR` and `instr_analyse.py DIR`.  Their outputs for the runs here are in `data/runs/` ([`blocks-table.md`](data/runs/blocks-table.md), [`blocks-analysis.txt`](data/runs/blocks-analysis.txt), [`blocks-control.txt`](data/runs/blocks-control.txt), [`io-analysis.txt`](data/runs/io-analysis.txt), [`instr-analysis.txt`](data/runs/instr-analysis.txt), and in the quiet rerun [`analysis-wall.txt`](data/runs/2026-10-29-quiet/analysis-wall.txt), [`analysis-cpu.txt`](data/runs/2026-10-29-quiet/analysis-cpu.txt) and [`io-analysis.txt`](data/runs/2026-10-29-quiet/io-analysis.txt)).  The two quiet-rerun analyses were produced with the research copy of `analyse.py` and `analyse_cpu.py` (`research/sorts/`), run with `old` as the baseline; they differ from `bench/`'s versions in their default baseline and in how they treat the `none-new` baseline (so their hash-check lines report the non-sorting baselines as mismatches, which they are by design).

Which table of the PR comes from which data: the table of inputs on which the old sort is quadratic is `data/runs/2026-10-28-blocks/` (analysis in `blocks-analysis.txt` and `blocks-table.md`); the table of random keys is the quiet rerun in `data/runs/2026-10-29-quiet/` for the time column and `data/runs/2026-10-28-instr/` for the instruction column; the `io_compute` paragraph is `data/runs/2026-10-29-quiet/io/` and its `io-analysis.txt`.  The method, the caveats (including a negative control that two of 19 workloads' intervals missed, and a CPU-time analysis too noisy to quote) and the machine load of every run are in [`data/README.md`](data/README.md).

## The research record

[`research/`](research/) is the design work behind the PR, in the order a reader would want it.  Its sources assume the layout of the research repository it was copied from, with the Lean harness in `sorts/` and the bench runner in `bench/` side by side, and that is the layout here: `research/sorts/` and `research/bench/`.

* [`research/sorts/`](research/sorts/): the research harness.  `Main.lean` and `Sorts/*.lean` hold the candidates: `Pdq.lean` (the algorithm that became the PR), `PdqLemmas.lean`, `PdqSorted.lean` and `PdqCost.lean` (its proofs), `PdqLab.lean` (one copy with every design knob switchable by name, such as `lab:lomuto,bl,c24`), `ThreeWay.lean` (three-way partitioning) and `Adaptive.lean` (the natural-run front end).  [`PLAN.md`](research/sorts/PLAN.md) has the pre-registered question, estimand and decision rule of each of the twelve rounds, written before the round ran, with the deviations recorded afterwards.  `cells.py` writes each round's plan (the generated `cells-*.json` are not kept), `shards.py`, `shuffled*.sh` and `analyse*.py` are the driver and analysis scripts, `go/main.go` is Go's `slices.SortFunc` as an outside reference, and `stabilizer/` builds the code-layout randomisation used to check that layout effects are small.
* [`research/bench/run.py`](research/bench/run.py): the randomised-block runner that `shards.py` calls.
* [`research/logs/`](research/logs/): each round's `README.md` (commit built, command, load), `runs.tsv` and `analysis*.txt`.  `qsort-round4-loaded` and `qsort-round7-loaded` are first attempts abandoned because the machine's load rose, kept as such.  Where a round's README mentions a `cells.json` copy, regenerate it with `sorts/cells.py ROUND CPU`.  Per-shard directories and the plans are left out where `runs.tsv` already merges them.
* [`research/partition/`](research/partition/): [`NOTES.md`](research/partition/NOTES.md) is the study of partition schemes, with `model.py` (a step-for-step Python model of the lab sort that counts comparisons and swaps by phase, checked against the Lean binary by output hashes), `trace*.py`, `stats-*.txt` (model output), `perfstat-*.txt` (hardware counters) and five timed rounds.
* [`research/specialisation/`](research/specialisation/): [`NOTES.md`](research/specialisation/NOTES.md) is the study of which helpers to compile once and which to specialise at each call site (code size against speed), with the variants' sources in `core-variants/`, the scripts in `tools/` and the size and timing logs in `logs/`.
* [`research/reviews/`](research/reviews/): the independent reviews that shaped the design.  `claude-break-triage.md` and `gemini-design-review-triage.md` are the triage of a fresh-context Claude's attempt to break the code and of a Gemini design review, with the raw logs and scripts beside them (`claude-break/`, `gemini-design-review.txt`); [`partition/`](research/reviews/partition/) holds two later break-it reviews of the partition candidates (command logs, generator scripts, sweeps and model comparisons).

## What was tried and rejected

All of this was measured on the benchmark machine with the harness above; each item names where the data is.  Ratios are against pdq as in the PR unless said otherwise.

**Three-way partitioning (lean4 pull request 14653).**  Round one ([`research/logs/qsort-round1/analysis.txt`](research/logs/qsort-round1/analysis.txt), 10 blocks, 100,000 elements) measured `threeway` against the current sort, pdq and `Array.mergeSort`.  Three-way partitioning removes the quadratic behaviour on many equal keys (`constant` and `dups4`, within a factor of 1.2 of pdq on those, `ThreeWay.lean`), but it keeps median-of-three's weaknesses: on the median-of-three killer `pathological` it is level with the current sort at about 1.08 [0.99, 1.17] of its time, where pdq is about 0.0001 of it, and on nearly sorted (2.05 [1.81, 2.33]) and organ-pipe input (1.73 [1.53, 1.95]) it is slower than the current sort.  Pattern-defeating pivot choice, pattern breaking and the heapsort fallback are what fix those, and a three-way partition does not provide them.

**One-directional (Lomuto) partitions, branch-free or not.**  Rounds four to ten and the partition study ([`research/partition/NOTES.md`](research/partition/NOTES.md)).  A one-directional partition, especially a branch-free one (as in Rust's unstable sort), was the one change that made the sort clearly faster than core's on random keys on the benchmark machine: about 0.75 of core's time on the 6,250,000 `UInt64` case in round twelve ([`research/logs/qsort-round12/analysis-vs-core.txt`](research/logs/qsort-round12/analysis-vs-core.txt)), and 0.42 to 0.46 of pdq's on random `Nat` (partition notes).  It loses on structured input: 1.2 to 1.7 times pdq on interleaved ascending runs and 1.3 to 1.4 on nearly sorted input (rounds five, six, nine and ten).  The partition notes explain why: a partition that keeps the order of the smaller side turns K interleaved runs into K shorter interleaved runs, the pivot sample then lands at the same bad positions again, and the range shrinks by a few elements per partition until the heapsort fallback runs.  A branch-free version of pdq's own two-ended partition that swaps exactly pdq's pairs (`bh`) avoids the fixed point, but wins less on random `Nat` (0.76 of pdq's cycles, against 0.44 for the one-directional loop) and loses on interleaved runs (1.6 times pdq on runs16) and on random records (1.25 times); the notes give the cause.  Round twelve applied a rule fixed beforehand (no workload above 1.15 against pdq) to the two best candidates and both failed it ([`research/logs/qsort-round12/README.md`](research/logs/qsort-round12/README.md)); the third stage of the partition notes then showed that the remaining losses, notably Musser's perfect-shuffle input for median-of-three, are properties of order-keeping partitions that no further special case removes.  Production stayed with pdq's two-ended partition.

**The heuristic fixes and why they failed (the break-it findings).**  The candidates in the previous item needed three added heuristics: pattern breaking on all three ninther groups (`brk9`), a rule that makes the partial insertion sort give up early (`pisx`, `pisx6`), and a rule that hands ranges that look presorted back to pdq's own loop (`pred`, `predm`).  Two independent break-it reviews ([`research/reviews/partition/`](research/reviews/partition/)) found inputs on which each version failed: `pisx6` turned sorted-plus-a-small-block inputs into n log n work (it gives up before repairing anything, where Go's five moves would have repaired some), the flip-count rule was biased by where its windows started and was fixed by moving them, and so on until the ablations showed the cost came from the order-keeping partition itself.  The partition notes record each fix, the model prediction, the measurement and the failure that followed.  The reviews of the version that became the PR found two real defects in it, fixed before the PR: a comparison that is not a strict weak order could chain splits of equal keys without counting against the heapsort limit (so the PR skips the equal-key test in the round after such a split), and the pattern-breaking index was bounded by the array length instead of the range (so the PR uses `r % len`); both are in [`research/reviews/claude-break-triage.md`](research/reviews/claude-break-triage.md).

**BlockQuicksort in Lean.**  Round ten measured a block partition (`lab:block,c24`, in `PdqLab.lean`) next to the other candidates ([`research/logs/qsort-round10/analysis.txt`](research/logs/qsort-round10/analysis.txt)): level with pdq on random `Nat` (1.00 [0.90, 1.11]), but 1.5 to 2.4 times pdq on interleaved runs, nearly sorted input, organ pipe and the median-of-three killer at 100,000 elements.

**A natural-run front end with in-place merges.**  Rounds two and three ([`research/logs/qsort-round2/analysis.txt`](research/logs/qsort-round2/analysis.txt), [`research/logs/qsort-round3/analysis.txt`](research/logs/qsort-round3/analysis.txt)) measured `Adaptive.lean`, which detects ascending and descending runs, merges them in place with rotations and falls back to pdq for the rest.  It halves the time on two interleaved runs (0.49 of pdq's) but costs more on many runs and on a sorted head followed by random data: 1.8 to 2.9 times pdq on 16 to 256 sorted blocks of random values, 1.2 to 1.4 on 64 to 256 interleaved runs, 1.5 on a sorted head of √n elements.  The variants that trust only a few long runs (`fewruns4`, `fewruns8`, `onerun`) were measured in round three on fresh data.  The reviews found the run bookkeeping carries no invariants and the moves are Θ(n log² n) on many sorted runs ([`research/reviews/claude-break-triage.md`](research/reviews/claude-break-triage.md)); it was dropped.

**Pseudo-random or golden-ratio sample positions.**  The third stage of [`research/partition/NOTES.md`](research/partition/NOTES.md): pivot sample positions that vary from level to level (`gold`, golden-ratio fractions; `hash`, hashed positions).  They remove the fixed point on interleaved runs on their own but cost more elsewhere: on pdq's own partition, 3 to 5% more instructions on random keys and worse pivots on three-run input, the median-of-three killer and Musser's shuffle (model counts in `stats-pos-sweep.txt`, `stats-pos-sweep2.txt`, hardware counts in `perfstat-screen9.txt`).  The quarter points that Go's pdqsort uses are better medians on ordinary shapes, so the PR keeps them.

**The insertion-sort cutoff.**  Round seven ([`research/logs/qsort-round7/analysis.txt`](research/logs/qsort-round7/analysis.txt)) swept 16, 20, 24, 32 and 48 against pdq's 12 with code layout sampled; round eleven confirmed production pdq with 24 against core on random keys.  The sweep's intervals mostly overlap on large random inputs (0.94 to 1.02 of pdq at 1,000,000 `Nat`), with the clearest gain on small arrays (arrays of 32: 0.69 to 0.92, 24 giving 0.80 [0.73, 0.89]).  24 is a choice within a flat region, not a sharp optimum.

**The specialisation split.**  [`research/specialisation/NOTES.md`](research/specialisation/NOTES.md): with every helper `@[specialize]`d, each of the 96 modules of core that call `qsort` receives a whole copy of the sort and `libleanshared.so` grows by 4.77% over the old one; compiling everything once costs 3.18 times the time at the 6,250,000 `UInt64` case (`closure` variant); sharing only heapsort, the partial insertion sort and the equal-key split (`c5b-hpe`) cut the growth to 2.19% at no measurable cost on random keys, but made nearly sorted input 1.9 to 2.8 times slower than pdq with everything specialised; sharing heapsort and the equal-key split only (`c5b-he`) keeps nearly sorted input and costs 3.25%, with only many equal keys paying (1.16 times the instructions, 1.06 times the time).  The PR uses the last of these, followed by one more restructuring (`shape-e`) that removed redundant copies of the recursion's tail and gave 249,621,984 bytes, 3.17% over the old 241,945,304.

## What this branch leaves out

Build outputs (`.lake`, binaries, the Go reference binary), the generated C of the specialisation study (`core-c/`, `harness-c/`; the study cites them but no number depends on them), the raw adversarial input files and hill-climbing inputs of the break-it reviews (hundreds of megabytes; their generators are in the review scripts), the largest trace files of those reviews, the generated `cells-*.json` of the research rounds (regenerate with `cells.py`), per-shard copies of data that `runs.tsv` already merges, and full test-suite logs duplicated by their targeted logs.
